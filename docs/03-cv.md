# 03 — CV

The section names and the copy quoted here are in Spanish: they are what gets
printed, and a parser maps them exactly as printed.

---

## 1. Two versions, not one

| Version | What for | Format |
|---|---|---|
| **CV-A** (designed) | WhatsApp, direct email, freelance client, download from the portfolio | Two columns, photo, color. A human opens it. |
| **CV-B** (`cv-ats`) | Computrabajo, Bumeran, LinkedIn Easy Apply, any form asking for a file upload | One column, no icons, no graphics. A machine parses it. |

The same facts in both: they come from the same dataset, the view changes. In
Argentina a photo is expected and a well-designed CV communicates product
judgement — which is why CV-A is not thrown away, it is duplicated.

Today only CV-B is rendered. The machinery already supports adding the other.

## 2. CV-B formatting rules

- One single column. No sidebars, tables, text boxes, headers or footers.
- Sections with standard names: `Perfil`, `Habilidades técnicas`, `Experiencia`,
  `Educación`. No "Mi stack" and no "Lo que me mueve".
- Dates in a consistent `MM/AAAA` format.
- No progress bars and no level dots: no parser reads them.
- File name: `Nicolas-Cribb-Barbaro-Full-Stack-Developer.pdf`.
- 1 page for startups, 2 for corporate or traditional LatAm.
- **Parsing test:** open the PDF, select all, paste into a text editor. If it
  comes out scrambled, the parser reads it just as badly.

## 4. Bullets: the pattern

The register of **responsibilities** ("implementé buenas prácticas", "optimicé
procesos manuales") is exactly the one the human layer reads as a template. What
works is **technical action + concrete object + outcome**.

Each bullet lives in the dataset as an `Achievement` with its `dimension`.
Covering different dimensions in each role avoids four bullets saying the same
thing:

`delivery` · `architecture` · `performance` · `ownership` · `collaboration` ·
`business`

## 6. Technical skills

Grouped, with no graphical levels:

```
Lenguajes: TypeScript, JavaScript, PHP
Frontend: React, Next.js, SolidJS, Vue 3, Tailwind CSS, Material UI, Jotai
Backend y datos: Node.js, REST APIs, Sanity (headless CMS), WordPress/WooCommerce
Testing: Playwright
Infraestructura: Docker, CI/CD, Cloudflare, monorepos, Git
Otros: Mapbox GL JS, desarrollo asistido por IA (Claude Code, Cursor)
```

**Contract rule 3:** no skill can be declared `core` if no achievement or project
references it. When the dataset was loaded, the validator already dropped `Git`
from `core` to `working` because of this.

What was removed from the old CV and why: `SVN` (nobody searches for it, it
suggests legacy environments), `Router`/`Query` nested under React (they are not
tools at that level; nesting them communicates that you do not prioritise),
`Java/Springboot` (if you are not going to defend it in an interview, it does not
add).

What was missing and is now there: **Mapbox GL JS** (it only appeared as "mapas
interactivos" in prose — the searchable term is the other one), **Playwright**
(testing appears in a good share of postings and separates mid from senior),
**WordPress** in the list and not only in a bullet.

## 8. Per-application checklist (10 minutes)

1. Read the full posting and note the 8-10 skills it mentions.
2. Check the exact variants: if it says "Vue.js", use "Vue.js". The schema's
   `aliases` allow emitting the exact form without editing data.
3. Adjust the `Perfil` block so it speaks to the role's problem.
4. Reorder `Habilidades técnicas` putting what the posting asks for first.
5. Pick the right surface: a form → `cv-ats`; email or WhatsApp → CV-A.
6. Verify LinkedIn says the same as the CV you are sending.
7. If the portal allows a message, write 3 lines specific to that company. It is
   what avoids the 62% discard for lack of personalisation.

**Do not send the same PDF to everyone.** It is the difference between a 40-60%
match and a 75%+ one.
