# 10 — i18n: the bilingual system and its workflow

Written 2026-09-02, when `content.en.json` and `/en/` shipped.

This document exists for one thing: so the next person editing the CV knows
**in what order** to touch the two datasets, and why the lock only checks one
direction. What each file does is already commented where it lives (see
`CLAUDE.md`'s file map); this is the workflow those files add up to.

---

## 1. The rule: Spanish is edited first, always

Spanish is canonical. Every edit to a fact — a new achievement, a reworded
`Prose.short`, a metric — starts in `content/data/content.es.json`. English is
always a translation of something that already exists in Spanish, never a
draft written straight into `content.en.json`.

That one-directional discipline is what makes `translation.lock.json` correct
with **one hash per Spanish string** and nothing recorded on the English side.
The lock only ever has to answer "did the Spanish text this English text was
translated from move since?" — a question with one direction. A lock trying to
also catch "did someone silently edit the English without touching the
Spanish" would need a second hash per field and a second check, for a mistake
this workflow does not allow to happen: there is no path that writes English
first.

## 2. The loop

1. Edit `content/data/content.es.json`.
2. Run `pnpm run test:i18n`. It names every path whose Spanish text no longer
   matches what is stamped in the lock — that is what changed, nothing more
   and nothing less.
3. Translate those paths, and only those paths, in `content/data/content.en.json`.
4. Run `pnpm run i18n:lock`. It re-stamps the lock to the CURRENT Spanish text.
5. Commit `content.es.json`, `content.en.json` and `translation.lock.json`
   together, in one commit. A commit carrying the Spanish change without the
   other two is a commit that shipped a stale English CV.

Step 2 is also what a reviewer runs to check a PR that touches the dataset:
green means the English side accounted for everything the Spanish side moved.

## 3. What is translated, and what is not

`scripts/i18n-fields.ts` walks the whole dataset and tracks every string leaf
**except** a denylist of key names (`NOT_TEXT`) — a denylist, not an allowlist,
on purpose: a new prose field is tracked the day it is added, which is the
safe direction to be wrong in. Three kinds of field are excluded, each for a
different reason:

- **Not text at all.** `id`, `slug`, `start`, `end`, `roleId`, `skillIds`,
  `priority`, `visibility`, and the rest of the structural or numeric fields.
  `Metric.before` / `after` are numbers with a unit baked into the string
  ("500 ms"); the unit does not change between languages, so the value is not
  translated — it is copied. Translating "500 ms" into "500 ms" would be the
  check flagging real work as missing.
- **Proper nouns.** `company`, `client`, `institution`, `Skill.name`. "Hogarth"
  and "TypeScript" have no English form to write.
- **Private, or a closed vocabulary.** `Metric.source` is the author's own
  interview note — no resolved view ever renders it, so an English version
  would translate text nobody reads. `Link.kind` is a tag out of a fixed union
  (`"github" | "linkedin" | …`), not prose.

Two fields need a path-specific override because the same key name means
different things in different places: `Project.name` is a title ("Mapas de
distritos electorales"), translated like any other prose, while `Skill.name`
using the same key is a proper noun. `LanguageSkill.name` is the odd one —
"Español" / "Inglés" is a WORD in the language it names, not an identifier for
it, so it IS translated, unlike every other `name` in the dataset. Both
overrides are matched by path (`projects.*`, `languages.*`), not by key alone,
which is why `Skill.name` stays excluded even though it shares the key `name`
with both.

## 4. What the lock cannot do

`i18n:lock` stamps whatever text is currently in `content.en.json` against
whatever text is currently in `content.es.json`. It has no opinion on whether
the English is a good translation, a bad one, or the Spanish text copy-pasted
verbatim and then re-stamped — the "no long field left untranslated" check in
`i18n.check.ts` catches an EXACT copy over 40 characters, not a lazy one. Run
`i18n:lock` without translating anything and the lock declares the work done.

This is the same shape of gap `format:data` and `og:local` already have:
`format:data` proves the JSON is canonically written, not that the data in it
is true; `og:local` re-stamps `og.lock.json` to whatever the card generator
currently produces, not to a card someone looked at. All three are gates
against **forgetting** — a commit that moved the source and left the derived
artifact behind. None of them is a gate against **lying** — a commit that
regenerated the artifact without doing the work it represents. That gap is
closed by review, not by tooling: the same discipline that reads a diff for a
wrong number before merging it reads a diff for an untranslated sentence dressed
up as one.

## 5. Where each language lives

| What | Lives in | Checked by |
|---|---|---|
| The author's text (achievements, roles, projects, prose) | `content/data/content.{es,en}.json` | `pnpm run test:i18n` |
| The site's own words (headings, button labels, "present", duration units) | `content/schema/messages.ts`, `Record<Locale, Messages>` | The TypeScript compiler — a missing key is a type error, not a runtime gap |
| Formatting that depends on the language (dates, durations, `~`/`aprox.`) | `format.ts`, `format-metric.ts`, `skill-groups.ts` — all take a `Locale` parameter | `pnpm test` |
| Which URL a language lives at | `/` and `/cv` for Spanish; `/en/` and `/en/cv` for English | `src/lib/anchors.ts` for the section ids, `no-client-js.check.ts`'s `PAGES_WITH_JS` for the two pages allowed to ship JS |
| The PDF's file name | `content/schema/pdf-filename.ts` — `_EN_` tag for English, nothing for Spanish | `pdf-filename.test.ts` |

`messages.ts` and the dataset are deliberately two different mechanisms
covering two different kinds of text, not one system that grew a special case.
The compiler is free and exhaustive for a **closed, small** set of strings
known at build time; the dataset is open-ended author's prose that grows one
entry at a time, and no compiler can check that a new achievement got written
in both languages. Putting chrome copy in the dataset would make `messages.ts`
redundant; putting the CV's achievements in `messages.ts` would make the type
system the reviewer, and it cannot tell a good English sentence from a bad one
any more than the lock can.

## 6. What is bilingual today, and what deliberately is not

Two things are true about the site as of `/en/` shipping: `/` and `/en/` are
both landings, both indexable; `/cv` and `/en/cv` are both `noindex`, reachable
only through the `#cv` anchor of their own landing, never linked directly.

**Bilingual today:**

- The landing (`/`, `/en/`) — hero, anchor index, knowledge map, projects,
  full CV, all through `messages.ts` and the dataset.
- The CV page (`/cv`, `/en/cv`).
- The CV PDF (`/cv.pdf`, `/en/cv.pdf`) — same layout, same handler
  (`functions/_handler.ts`), different `Locale`.
- All of the chrome copy above: section headings, the download buttons, the
  ES/EN switch itself.

**Still Spanish only, on purpose:**

- **`/llms.txt` and `/cv.json`.** Both agent-facing endpoints call
  `content.getView(surface, "es")` with the locale hardcoded, not read from a
  request. This is a deferral, not an oversight: an agent reading the CV
  programmatically is a different audience from a recruiter reading the
  landing, and giving it a second slice of surface area — content negotiation,
  or an `/en/llms.txt` sibling — was not part of what this slice asked for.
  **When to reconsider:** the day either endpoint's consumers are shown to
  need English, add the same locale parameter `getView` already takes
  everywhere else.
- **The OG social card.** `public/og.jpg` is one committed image for both
  locales; only `og:locale` and the image's `alt` text vary by language in
  `Base.astro`. Sharing `/en/` on LinkedIn or WhatsApp shows the Spanish card.
  Regenerating a second card is real work — `build-og.ts` renders text into a
  fixed layout, and an English card needs the English strings measured and
  positioned the same way the Spanish ones were — and nothing in this slice
  needed it to ship. **When to reconsider:** the day the English CV is
  actively shared as a link on its own, not only reached by switching language
  from the Spanish landing.
- **The 404 page (`src/pages/404.astro`).** There is no `/en/404`: a broken
  URL under `/en/` still renders the Spanish 404, with links back to the
  Spanish landing's anchors. A visitor who mistyped an English URL gets a page
  in the other language rather than nothing — an acceptable trade for a page
  Cloudflare serves automatically and that carries no chrome copy budget of
  its own. **When to reconsider:** the day the English landing gets enough
  traffic that a Spanish error page for it stops being a rounding error.

`hreflang` is emitted on the two indexable landings only: `es` → `/`, `en` → `/en/`, `x-default` → `/` (Spanish, because the market is LatAm, not a browser-language guess). It is absent from `/cv` and `/en/cv` since both are `noindex`. The sitemap carries reciprocal `es`/`en` relations only because `@astrojs/sitemap`'s `i18n` option has no slot for a third alternate on URLs two others already claim — the `<head>` tags carry the authoritative `x-default`. See `docs/09-seo-and-metadata.md` §2.3 for the reasoning and enforcement.
